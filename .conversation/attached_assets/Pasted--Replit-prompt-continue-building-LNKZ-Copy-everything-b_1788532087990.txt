## Context

I am building **LNKZ**, a self-hostable MCP server that carries conversation context between
people, devices, and LLM clients. Repo: https://github.com/nsirivolu27/LNKZ (branch
`lnkz-mcp-relay`).

**Stack:** TypeScript throughout. Node 22. Express 5. `@modelcontextprotocol/sdk`. Zod for
validation. SQLite via Node's built-in `node:sqlite` with FTS5. Web client is plain
TypeScript with Vite, no framework. Tests are `node:test`, 44 of them, plus
`scripts/smoke.mjs` which boots the built server and drives it over REST and MCP.

**What exists today:**

- `mcp-server/src/store/` conversation storage, handoffs, audit log
- `mcp-server/src/import/` normalizers for ChatGPT, Claude, Gemini, Markdown, plain text
- `mcp-server/src/intel/` decision extraction, context packets, redaction, conflict detection
- `mcp-server/src/connectors/` Slack, Jira, Figma, doc feeds, MCP-to-MCP federation
- 20 MCP tools, 4 resources, 4 prompts over Streamable HTTP and stdio
- A REST API and a web console at `/console.html`
- One shared API key for the whole server. No accounts. No users. No tenancy.

Read `ARCHITECTURE.md`, `MCP.md`, and `AGENTS.md` before writing code. `AGENTS.md` has the
boundaries I care about.

## What I want you to build

Two things, in this order. Do not start the second until the first is done and tested.

### Phase 1: real identity and server-enforced authorization

LNKZ has no concept of a user. A single shared key grants everything. That is fine for one
person on a laptop and unacceptable for anything hosted. Build:

1. **Accounts.** Email plus password. Argon2id, or bcrypt with cost 12 or higher. Never store
   a plaintext or reversibly encrypted password. Include a password strength floor and reject
   known-breached passwords if you can do it without an external service call at signup time.

2. **Workspaces.** A user belongs to one or more workspaces with a role: `owner`, `member`,
   `viewer`. Every conversation, handoff, and audit event belongs to exactly one workspace.

3. **Sessions.** HTTP-only, `Secure`, `SameSite=Lax` session cookies. Server-side session
   records so a session can be revoked. Absolute and idle expiry. Rotate the session
   identifier on login and on privilege change.

4. **Scoped API tokens.** Replace the single `LNKZ_API_KEY` with per-user tokens that carry a
   workspace and a scope. Store only a hash. Show the token once at creation. Support
   revocation and an expiry. Keep `LNKZ_API_KEY` working as a bootstrap admin token so
   existing setups do not break, but log loudly when it is used.

5. **Authorization enforced in the data layer, not the route layer.** Every `ConversationStore`
   method takes an actor (user id plus workspace id plus role) and filters on it in SQL. A
   route that forgets to check permissions must still return nothing, because the query itself
   is scoped. This is the single most important requirement in this phase.

**Critical constraint:** do not break the `ConversationStore` interface contract or the MCP
tool surface. The MCP tools, the REST API, the stdio server, and the web console all call the
same store. Extend the interface, do not fork it.

**The specific attack I need you to defend against and test for:**

A common failure in AI-built apps: the client stores the user's role in `localStorage` and the
UI reads it to decide what to show. Anyone can open DevTools, go to Application, Local
storage, change `role` from `member` to `admin`, refresh, and the admin panel appears. The
data behind it loads too, because the server trusted the client.

So:

- The browser must never hold a role, permission, entitlement, or feature flag that any
  server decision depends on. Client state controls presentation only.
- Every privileged read and write re-derives the actor's role server side from the session.
- Write an integration test that logs in as a `member`, tampers with every piece of client
  state the app sets, calls the admin-only endpoints directly, and asserts 403 on all of them.
- Write a second test asserting that a `member` in workspace A cannot read, update, delete, or
  create a handoff for any resource in workspace B, by id, even with a valid session.

Also note: the web console currently keeps the API key in `sessionStorage`. Once real sessions
exist, remove that entirely. The console should authenticate with a cookie and hold no
credential in JavaScript-reachable storage.

## Rules

- **Tests stay green.** `npm test`, `npm run typecheck`, `npm run build`, and
  `node scripts/smoke.mjs` all pass before you call anything done. Extend `scripts/smoke.mjs`
  to cover the new auth flow end to end.
- **Small, reviewable commits.** One concern per commit, with a message that explains why, not
  just what.
- **Human-readable code.** Clear names, no cleverness, comments where a reader would ask why.
- **Do not add a framework.** No React, no Next, no ORM. The web client is plain TypeScript on
  purpose and the SQL is hand written on purpose.
- **Do not break MCP.** The tool names, input schemas, and output shapes are a public contract.
  Additive changes only. If a tool must change, say so and wait for me.
- **Migrations, not resets.** There is existing data. `PRAGMA user_version` migrations exist in
  `store/sqlite.ts`. Follow that pattern and write the backfill that puts existing rows into a
  default workspace.
- **No secrets in the repo, in logs, or in error messages.** Handoff tokens especially: they
  are bearer secrets and must never be logged.

## Definition of done

- I can sign up, create a workspace, invite someone as a `viewer`, and confirm they cannot
  write.
- A `member` who tampers with every scrap of client state gains nothing.
- Two users in different workspaces cannot see or touch each other's conversations, by id or
  by search.
- Every item in the Phase 2 table is either implemented or has a written reason it does not
  apply.
- CI is green, including the new dependency scan.
- `ARCHITECTURE.md` has a section on the authorization model, and `ROADMAP.md` moves the
  shipped items out of "Next".
