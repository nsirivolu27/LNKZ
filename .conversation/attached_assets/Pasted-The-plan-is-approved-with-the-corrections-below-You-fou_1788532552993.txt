## Corrections

### 1. Do not build the blind-token search index. Do not encrypt message bodies in this pass.

You correctly spotted that encrypting messages while FTS5 holds their plaintext is theatre.
That was a good catch. The conclusion is the wrong one.

A keyed blind-token index destroys the thing this product is best at. You lose BM25 ranking,
porter stemming, and snippet(), which means search stops ranking and stops explaining why
something matched. That is a serious product regression bought for a threat model that does
not apply yet: LNKZ is single-tenant and self-hosted, the operator owns the disk, and anyone
who can read the SQLite file can also read the master key from the environment of the process
sitting next to it.

So for this pass:

- Encrypt connector credentials with AES-256-GCM and a key from the environment. Those are
  third-party secrets and genuinely need it.
- Leave conversation content in plaintext at rest, and write down in ARCHITECTURE.md that the
  database file is the security boundary, that operators should use an encrypted volume, and
  what would have to change for at-rest content encryption to be real.
- Revisit this when LNKZ is actually multi-tenant and the operator is not the data owner. Put
  it in ROADMAP.md with the search tradeoff stated, so the next person does not rediscover it.

Naming the tension and deferring it deliberately is a better engineering answer than shipping
a weaker product to satisfy a checklist item.

### 2. Use node:crypto scrypt, not bcryptjs.

You chose bcryptjs to avoid a native compilation barrier. Right instinct, wrong tool. Node has
crypto.scrypt built in: native speed, memory-hard, zero dependencies, and it keeps the property
this whole project is built on, which is that `npm install` never needs a compiler.

bcryptjs at cost 12 in pure JavaScript takes hundreds of milliseconds of pure CPU and, if you
reach for the sync API, blocks the event loop on every login.

Use the async callback form, promisified. Parameters: N = 32768, r = 8, p = 1, 64-byte derived
key, 16-byte random salt. Store as scrypt$N$r$p$<salt-b64>$<hash-b64> so the parameters travel
with the hash and can be raised later. Compare with timingSafeEqual. Write the verifier so an
unknown algorithm prefix is a clean failure, not a crash, which is what lets you migrate to
argon2id later without a flag day.

### 3. /mcp is bearer-only. It must never accept a cookie.

You are adding cookie sessions to an app that already has a state-changing POST /mcp. If that
endpoint accepts cookie authentication, every MCP tool becomes reachable by cross-site request
forgery, and delete_conversation is one of those tools.

POST /mcp authenticates by bearer token only. A request carrying a session cookie and no bearer
is rejected. Same rule for any future endpoint that takes an action without a same-origin form
flow.

While you are there, write down the CSRF posture for the cookie-authenticated routes in
ARCHITECTURE.md: what SameSite=Lax covers, what the existing validateOrigin middleware covers,
and where the gaps are. If you conclude a token is needed, add one. Do not leave it undecided.

### 4. Cross-workspace access returns 404, never 403.

You wrote "not found or forbidden without leaking existence." Pick one and make it uniform: a
resource in another workspace returns 404, always, for every method. A 403 tells an attacker
the id is real, which is exactly the leak you were trying to close.

403 is reserved for one case only: the actor is in the right workspace but their role does not
permit the action. Test both paths.

### 5. stdio fails closed.

"An explicitly configured local actor" is right, but say what happens when it is absent. The
stdio server must refuse to start with a clear error naming the environment variable it needs.
It must never fall back to a default workspace, an implicit owner, or the bootstrap actor. A
misconfigured local server that silently grants everything is worse than one that will not boot.

## Additions to Phase 1

Back up before migrating. The v1 to v2 migration mutates a live database with real data. It
must copy the database file to <path>.v1-backup-<timestamp> before touching anything, refuse to
proceed if that copy fails, and log the path. Document the rollback in DEPLOY.md.

Pin the capability matrix in code and in a test. Write it as a table in ARCHITECTURE.md and
enforce it in one place, not scattered across methods:

| Capability                                  | owner | member     | viewer |
|---------------------------------------------|-------|------------|--------|
| Read conversations, search, packets          | yes   | yes        | yes    |
| Create, update, append, delete conversations | yes   | yes        | no     |
| Create handoffs                              | yes   | yes        | no     |
| Revoke handoffs                              | yes   | own only   | no     |
| Read audit log                               | yes   | own actions| no     |
| Invite, remove members, change roles         | yes   | no         | no     |
| Create and revoke API tokens                 | yes   | own only   | no     |
| Rename or delete workspace                   | yes   | no         | no     |

A viewer creating a handoff would be a read-only role that can grant read access to anyone,
which is not read-only. That is why it is a no.

The tamper test is Phase 1, not Phase 2. Write an integration test that:

1. Logs in as a member
2. Sets every client-writable value the app touches to admin, owner, and a foreign workspace id
3. Calls every owner-only endpoint directly with that session
4. Asserts 403 on all of them, and that no response body differs from the untampered case

Then a second test: a member of workspace A, holding a valid session, cannot read, search,
update, delete, append to, or mint a handoff for any resource in workspace B, addressed by
exact id. Assert 404 on all of them.

Extend scripts/smoke.mjs in Phase 1. The auth flow is Phase 1, so its end-to-end proof is too.
Add: signup, login, session cookie round trip, workspace creation, invite, scoped token
creation, a token-authenticated MCP call, logout, and a rejected request after logout.

Rate limit handoff redemption per token, not only per IP. A handoff token is guessable in
principle. Cap total failed redemption attempts against a given conversation and back off.

Do not weaken existing tests to make them pass. All 44 will need an actor threaded through
them. That is expected and it is mechanical. If a test becomes hard to satisfy, that is a
finding about the design; tell me rather than loosening the assertion, deleting the test, or
skipping it.

Do not enumerate accounts. Signup with an existing email, login with a wrong password, and
invite acceptance must not reveal whether an account exists. Same response, same shape, same
timing envelope.

## Explicit deferrals

State these in ROADMAP.md rather than silently omitting them:

- Password reset and email verification, which need an email transport LNKZ does not have
- Two-factor authentication
- SSO and OIDC
- At-rest encryption of conversation content, with the search tradeoff written down
- A shared rate-limit store for running more than one instance
