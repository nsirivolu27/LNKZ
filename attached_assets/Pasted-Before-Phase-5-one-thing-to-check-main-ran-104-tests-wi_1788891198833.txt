## What this phase is

A person accumulates conversations across weeks and clients. Search alone is not organization. This phase adds grouping, and nothing more.

## Build

- A `Project` record: id, name, description, created and updated timestamps, scoped to `workspace_id` like everything else in the store.
- Conversation membership in zero or more projects. Membership is a join table, not a field on the conversation. A conversation handed to you can belong to your project without changing the conversation itself, and that distinction is the whole reason for the join.
- Store methods on the `ConversationStore` interface, implemented in both SQLite and Postgres. Adding a method to the interface without implementing it in both is exactly the bug that shipped once already with `ListOptions.originInstance`: it typechecked, it read as though it filtered, and it silently returned everything.
- A migration for each store, versioned the way the existing ones are. Do not hand edit an existing migration; add a new one.
- MCP tools: create a project, rename a project, delete a project, add and remove conversations, list projects, list one project's conversations.
- Resources: `lnkz://projects` and `lnkz://projects/{id}`.
- Project scoping on existing surfaces. `list_conversations`, `search`, the lineage graph and context packet building each take an optional project filter. When the filter is absent, behavior is unchanged.

## Constraints

- A project is organization inside one instance. It is not a shared workspace, it grants nobody access to anything, and it does not travel with a handoff. If a project id would ever appear in a `lnkz.conversation.v1` packet or in lineage, you have built the wrong thing.
- Deleting a project deletes memberships and nothing else. Conversations survive.
- A conversation that arrives from another instance can be added to a local project like any other. Nothing about being imported makes it special here.
- No new dependency for this. It is two tables and a filter.
- Never log project contents or conversation bodies.

## Done when

- A conversation can belong to two projects at once, and appears under both.
- A context packet built with a project filter contains only that project's conversations, and the token budget still holds.
- Deleting a project leaves every one of its conversations intact and searchable.
- The same test file passes against both SQLite and Postgres, with the Postgres cases skipping cleanly when `LNKZ_POSTGRES_TEST_URL` is unset.
- A project filter naming an id that does not exist returns empty, not everything. Write that test specifically. It is the failure mode that already happened once.
- `tests/round-trip.test.ts` still passes untouched, and the total test count is higher than it was at the start of this phase.
