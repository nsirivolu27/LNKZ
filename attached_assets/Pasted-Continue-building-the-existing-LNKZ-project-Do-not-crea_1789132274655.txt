Continue building the existing LNKZ project. Do not create a new app or replace the current architecture.

Project goal:
Turn LNKZ into an interview-ready, configurable conversation context platform for personal users and teams. LNKZ stores conversations, creates context packets and handoffs, and exposes the same workspace through the standalone lnkz-mcp MCP adapter.

Repository boundaries:
- LNKZ repository: REST API, authentication, workspace configuration, storage, search, imports, handoffs, dataset preparation, web UI, and Expo mobile app.
- lnkz-mcp repository: MCP adapter only. It must call the LNKZ REST API and must not contain its own database or duplicate business logic.

Build requirements:

1. Mobile application

Finish the Expo mobile app so it works end-to-end against the real LNKZ backend.

The mobile app must support:

- Connecting to a LNKZ server with URL and API key
- Securely storing the API key using SecureStore on native devices
- Browser local storage for web preview
- Displaying the authenticated workspace name, workspace mode, use case, actor, and scopes
- Showing live conversation, message, provider, and handoff statistics
- Listing conversations from the backend
- Opening a conversation and viewing its analysis
- Searching conversations
- Importing ChatGPT, Claude, Gemini, Markdown, plain text, and LNKZ exports
- Creating, sharing, continuing, and revoking handoffs
- Showing connector readiness and clear error messages
- Retesting the connection with the stored key
- Disconnecting and clearing local credentials
- Handling loading, empty, offline, unauthorized, unavailable, and server-error states

Do not use hard-coded demo data once the API is connected.

3. REST endpoints

Implement or verify:

GET /api/workspace

Response:

{
  "workspace": {
    "id": "...",
    "name": "...",
    "mode": "personal",
    "useCase": "...",
    "datasets": {
      "enabled": true,
      "approvalTag": "training-approved"
    }
  },
  "access": {
    "actorId": "...",
    "scopes": ["admin","mcp","read","write"]
  }
}

POST /api/datasets/export

This endpoint must:

- Require authentication
- Require admin scope
- Require dataset export to be enabled for the workspace
- Require acknowledgeRights=true
- Accept explicitly selected conversation IDs
- Reject conversations outside the authenticated workspace
- Require the approval tag
- Preserve the original conversations
- Redact secrets, email addresses, cards, tokens, JWTs, private keys, and connection strings
- Produce deterministic train and validation JSONL
- Use a configurable seed
- Keep related lineage conversations in the same split
- Remove exact duplicate examples
- Include source IDs, timestamps, checksums, skipped records, and redaction counts
- Enforce a safe output limit
- Never claim that a model was trained

Use this response shape:

{
  "manifest": {
    "format": "lnkz.dataset.v1",
    "datasetId": "...",
    "workspaceId": "...",
    "seed": "lnkz-v1",
    "examples": {
      "train": 0,
      "validation": 0,
      "duplicates": 0
    },
    "sources": [],
    "skipped": [],
    "redactions": {},
    "checksums": {},
    "limitations": []
  },
  "trainJsonl": "...",
  "validationJsonl": "..."
}

4. MCP adapter

In lnkz-mcp:

- Add get_workspace
- Add export_training_dataset
- Add lnkz://workspace
- Keep all existing MCP tools and resources

- Never add a database to lnkz-mcp

5. AWS infrastructure

6. Backend and data boundaries

- SQLite remains suitable for local personal development.
- PostgreSQL is required for multi-workspace deployments.
- Enforce tenant isolation through authenticated request context and PostgreSQL RLS.
- Keep conversation intelligence deterministic and model-free.
- Do not call an LLM from the backend unless explicitly configured later.
- Treat dataset export as curation and preparation, not model training.
- Keep external connector credentials instance-scoped and document that limitation.
