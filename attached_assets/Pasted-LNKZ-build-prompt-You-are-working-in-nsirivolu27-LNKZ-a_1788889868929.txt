What this product is

One path, walked end to end:

Someone has a conversation with a model.
They hand it to another person.
That person picks it up on their own LNKZ instance and carries it forward.
The chain shows where it came from and who continued it.

Everything else serves that path. Context packing and token budgeting are features of step 3, not the thesis. LNKZ is federated by decision: every person runs their own instance, conversations move as copies, the recipient pulls and nothing accepts unsolicited writes. There are no accounts, no invites and no shared tenancy. Do not add any.

Phase 4: instance identity

Right now a received packet carries an origin URL and nothing else. A recipient cannot tell whether a packet actually came from the instance it names, and lineage.originInstance is an unverified string. Fix that.

Build:

An Ed25519 keypair per instance, generated on first start and persisted with the store. The private key never leaves the process, is never logged, and is never included in any packet, resource, error or health response.
GET /.well-known/lnkz.json serving the public key, a stable instance id derived from it, and an operator chosen display name. No authentication on this endpoint; it is public by design.
Packet signing on the sending side. Sign a canonical serialization of the packet, not a JSON string whose key order can vary. Put the signature and the signing instance id in the envelope, not inside the conversation body.
Verification on the receiving side, in transfer.ts. Fetch the sender's /.well-known/lnkz.json through the same SSRF guards as everything else, verify the signature, and record the outcome in lineage as a new field. Verification failure must not throw away the conversation; it must mark it unverified and let the operator decide.
A display name in the graph and in lnkz://transfers, falling back to the bare origin URL when identity cannot be fetched.

Constraints:

LNKZ_MCP_CONTEXT_SECRET is the trusted node forwarding HMAC. It is a different mechanism for a different purpose. Never reuse it for signing, and never derive one from the other.
Keep every SSRF protection in transfer.ts exactly as strict for the identity fetch as for the packet fetch. Do not add a bypass for well known URLs.
Never log keys, signatures, packet bodies, handoff tokens or message content.

Done when: a packet signed by instance A and altered in transit fails verification on B; an unaltered one passes; an instance with no reachable identity document still imports, marked unverified; and the round trip test still passes with verification recorded at both crossings.

Phase 5: projects

A person accumulates conversations across weeks and clients. Search alone is not organization. This phase adds grouping, and nothing more.

Build:

A Project record: id, name, description, created and updated timestamps, scoped to workspace_id like everything else.
Conversation membership in zero or more projects. Membership is a join, not a field on the conversation, because a conversation handed to you can belong to your project without changing the conversation itself.
Store methods on the ConversationStore interface, implemented in both SQLite and Postgres. Adding a method to the interface without implementing it in both is the exact bug that shipped once already with ListOptions.originInstance.
MCP tools: create a project, add and remove conversations, list projects, list a project's conversations.
A lnkz://projects resource, and lnkz://projects/{id} for one project.
Project scoping on existing surfaces: list_conversations, search, the graph and context packet building all take an optional project filter.

Constraints:

A project is organization inside one instance. It is not a shared workspace, it grants no one access to anything, and it does not travel with a handoff. If a project id would ever cross an instance boundary, you have built the wrong thing.
Deleting a project must not delete conversations.

Done when: a conversation can be in two projects, a packet built from a project contains only that project's conversations, deleting a project leaves its conversations intact, and both stores pass the same test suite.

Phase 6: execute_publish

publish/prepare.ts already shows the exact call to a remote MCP tool. This phase actually makes it. Read the comment at the top of that file first; it explains why the split exists.

Build:

execute_publish: takes what prepare produced, and invokes it against a configured target from LNKZ_MCP_TARGETS.
An explicit allowlist. A target is not publishable because it is configured; it is publishable because the operator named it in a separate allowlist variable. Absent allowlist means nothing can be published, in every environment, not just production.
An audit entry per attempt, recording actor, target, tool, conversation id, outcome and timestamp, in both stores, whether the call succeeded or failed.
Redaction before send, using the existing intel/redact.ts, on by default.
Idempotency. A retried publish must not create a second Jira issue. Key it on conversation id plus target plus tool.

Constraints:

Fail closed everywhere. A missing allowlist, an unparseable target, a write tool that was not explicitly permitted: all refuse, none guess.
Never log the payload. Log the decision and the outcome.
Do not weaken looksLikeWrite in prepare.ts to make a target easier to use.

Done when: publishing to a target absent from the allowlist refuses with a clear message and writes an audit entry; the same publish run twice creates one issue; redaction strips a planted credential before the call is made; and a failed remote call is recorded rather than swallowed.
